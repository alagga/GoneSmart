**Purpose:** This is the canonical, continuously maintained entry point for any assistant, coding agent or contributor working on GoneSmart with the maintainer. Read this file **before** changing code. Follow the detailed linked documentation for individual features; do not attempt to infer the latest implementation solely from old chat summaries.

**Last consolidated:** 2026-09-25. **Current development branch at consolidation:** feature/multi-playlist-add. This file consolidates explicit decisions from the available current and earlier coding chats and the existing repository docs. Historical chats may contain further details that were not recoverable; do not invent missing agreements. If the maintainer clarifies a rule, update this file.

## 1. Authority, continuity and keeping this file current

- Explicit current instructions from the maintainer take priority over this file. This file captures standing agreements; linked feature documents capture more detailed behavior; the checked-out code and tests establish what is actually implemented. Dated device logs describe observations, not universal guarantees.
- **Whenever the maintainer adds, changes or clarifies a recurring coding rule, update this AGENTS.md in the same GitHub work as the relevant code.** Amend the relevant section and its date/decision note. Update any affected feature docs, tests, README, FAQ, in-app Help or release notes as appropriate. Avoid maintaining a second, divergent rules file.
- Start every new chat or coding session by reading AGENTS.md on the **current development branch**, then the relevant linked documents, recent commits and CI status. Check the branch head before editing. If a rule conflicts with the current user's instruction, confirm or follow the explicit new instruction, then document the superseding decision. Never silently treat a provisional debug experiment as a final rule.
- Work from the GitHub repository rather than reconstructing source from chat snippets. If GitHub access is not connected in a new chat, ask the maintainer to connect the GitHub integration or supply the file; do not pretend to have read the latest repository.
- Communicate with the maintainer in **German**. Explain work and testing concisely and clearly, especially where GMMP internals are uncertain. The repository's public documentation and the companion app use English.

**New-chat handoff:** Read this file first; read the relevant feature docs under docs/; inspect the active branch, latest commit and CI; then inspect the actual relevant source files. Continue from confirmed device results and unresolved issues, not from an assumed green state.

## 2. Identity, scope and architecture

- Repository: **alagga/GoneSmart**. Android application ID/package: **io.github.alagga.gonesmart**. Visible app name: **GoneSmart**. LSPosed/Vector target scope: **gonemad.gmmp**. The local Android Studio project has been kept at C:\Android\Projects\GoneSmart.
- The tested target for the current obfuscated hooks is **GoneMAD Music Player (GMMP) 4.2.0**. libxposed API **102**. Android/Kotlin, Gradle Kotlin DSL, companion app plus module. Never claim a different GMMP or framework version works without testing it.
- GoneSmart extends GMMP rather than replacing its playback engine. GMMP owns playback, its queue lifecycle, Auto-DJ request timing, existing queue-size settings and normal controls. Smart Auto-DJ replaces **track selection only** when enabled; native GMMP Auto-DJ remains the configurable fallback. GoneSmart is controlled from its **own companion app**, not by inventing a fifth GMMP Auto-DJ mode.
- The main external recommendation inputs are **ListenBrainz and Last.fm**, matched only to tracks actually in GMMP's local database. No provider suggestions are streamed. Limit network searches and retries as documented in docs/ARCHITECTURE.md and docs/PROVIDERS.md; do not casually change the established selection/fallback algorithm when working on UI.
- Optional UI features (multi-playlist selection, playlist folders, Flip, Track Auto-DJ) are independent of Smart DJ unless their documented action explicitly enables it. Prefer isolated, version-guarded hooks. Passive hooks must preserve the original GMMP result/side effects (call the original chain); intercept or alter behavior only for the specifically enabled feature and verified target.
- Obfuscated GMMP classes and fields are **version-specific observations**, never a stable upstream API. Verify model bindings and callbacks from actual code/device logs, fail closed to native GMMP behavior if a hook or complete model is unavailable, and do not guess dangerous write methods.

See docs/ARCHITECTURE.md, docs/PROVIDERS.md, docs/BUILDING.md and the feature-specific docs below.

## 3. Repository work, code delivery and release discipline

- Make code changes **directly in the connected GitHub repository**, on the active development/feature branch, in reviewable commits. Do not force-push, unexpectedly overwrite unrelated work or silently merge experimental features into main. Read the current branch head before committing; verify that it has not advanced. Keep the user's local and GitHub projects synchronized by providing the commit/branch.
- **When giving manual source edits in chat, provide the COMPLETE content of EACH changed file**; no partial snippets or diffs as the sole delivery. When changes have already been committed to GitHub, normally give the commit and relevant file paths instead of pasting huge files unless the user asks for them.
- For any new installable debug build: implement and combine related fixes, add focused automated regression tests, commit, wait for the GitHub Actions **Unit tests**, **Build debug APK**, **Build release APK (unsigned smoke test)** and **Upload debug APK** steps, and give the actual run/commit plus **direct GitHub artifact link**. If CI fails, inspect the failing logs and fix the build before asking for phone testing. Never invent an APK URL or say CI passed when it has not.
- Batch closely related changes and useful diagnostics into **one device-test build** whenever safe. The maintainer does not want ten successive debug APKs for issues that can be investigated together. Produce a short, consolidated test checklist. **Do not ask to repeat already verified device tests** unless relevant code or GMMP/framework version changed, or new evidence indicates a regression. Do not treat CI compilation/unit tests as proof of runtime stability: confirm Android/GMMP/LSPosed behaviors on the real device when necessary.
- On crashes, first analyze the **complete Logcat/AndroidRuntime stack**, relevant GoneSmart tag and framework/Vector logs; add bounded intermediate diagnostics if needed. Avoid blind speculative hook changes. Filter package:gonemad.gmmp for complete crash reports; narrower relevant tags include GoneSmart, GoneSmartPlaylist, GoneSmartFlip and GoneSmartTrackMix. Include the exact tested APK/commit when correlating a log. Redact private paths/track data before publishing.
- A module update normally requires installing the new APK and force-stopping/restarting GMMP so the injected code is reloaded. Do not routinely require a reboot or framework reinstall without evidence.
- A **signed public release** follows docs/RELEASING.md: reviewed feature branch/PR to main, versionCode/versionName and release notes, green CI, GitHub Actions release signing using the *existing* permanent release key and the stable/prerelease option. Do not publish a new release just because a debug CI run is green. The maintainer prefers completing and validating the planned v0.4.x changes together before one collected release.
- Maintain README, FAQ, Installation/Building, feature docs, **docs/DESIGN_SYSTEM.md**, in-app Help and release notes when a feature is finished or its public behavior changes. Keep established functionality and tests intact when making unrelated changes. The user's instruction explicitly requires **both GitHub documentation and overall GoneSmart in-app Help**, not one instead of the other.

## 4. Language, terminology and translations — standing rule

**This distinction is non-negotiable:**

1. The **GoneSmart companion app is entirely English**, including tabs, settings, Help, FAQ, Logs labels, notifications and newly introduced options. Do not translate the companion app into German simply because the maintainer chats in German or the phone is set to German. Keep existing feature terminology consistent.
2. **Everything injected into GMMP's menus, dialogs, status/success messages and contextual UI should use the currently installed GMMP's native localized resources**, in the player's current language. Avoid hardcoded English/German text and a separate, incomplete hand-maintained translation table inside GMMP. Known resource examples from verified features: num_selected, add_to_playlist_toast, playlist, playlists, track, auto_dj and GMMP's localized Play/Queue/started terms. Check the installed GMMP version's real resource names, grammar and plural forms rather than assuming they never change.
3. Where composing a feature label, reuse the native player's own translated terms; for example companion **Track Auto-DJ** remains English while native GMMP can show German **Titel Auto-DJ** or English **Track Auto-DJ**. For a truly missing GMMP string, use a verified native fallback or a clear neutral icon/behavior; **do not invent a foreign-language translation**. Debug-only internal logs may be English. Newly introduced GoneSmart-only labels inside GMMP that cannot be assembled from GMMP resources require an explicit localization approach rather than an unlocalized production string.
4. Reuse native selection counters and native-style result texts. Avoid several duplicated Toasts/Snackbars for one action. Successful multi-add reports file count and successful destination count **once**; Track Auto-DJ likewise displays one verified success confirmation. Genuine errors remain visible.
5. Preserve official GMMP wording where possible rather than silently renaming native functions; use **Track Auto-DJ** consistently in the English companion. The stored internal Logs category name [Track Mix] is a legacy contract; user-facing English labels are **Track Auto-DJ** as documented in docs/LOGGING.md.

Sources of detail: docs/DEVELOPMENT_MULTI_PLAYLIST.md, docs/TRACK_MIX_TESTING.md, docs/QUEUE_FLIP_TESTING.md and docs/LOGGING.md.

## 5. GMMP design and theme integration — standing rule

- The optional injected UI should look and behave **as though GMMP built it**. Match the **actual active GMMP view mode/skin**, row height, headline font family and size, padding, icon alignment, selectable ripple, background, menu/FAB style and selection behavior. No invented separator lines where the original has none. Do not mistake a small metadata TextView for the primary playlist headline. Show the true native playlist display name, not the M3U filename.
- **Never hardcode or approximate GMMP runtime design values when the native view already exposes them.** This includes colors, font size, font scaling, Typeface, TextAppearance/spans, row height, padding, margins, gravity, ripple/background, selection state, FAB style and layout/view-mode structure. Clone/read the **actual currently-bound native view** and its styled text at runtime, including Android font-scale/device-density effects. Static px/sp multipliers, guessed ratios such as “30 px → 45 px”, screenshot-derived constants and one-device tuning are acceptable only as explicitly documented **defensive fallbacks when no native source exists**, never as the primary implementation. Follow the live GMMP Aesthetic/theme sources (current primary, accent, native FAB color, surface/background and text state). The user may set a manual color or enable a dynamic palette derived from the playing cover; update visible UI, selection highlights and branded decoration when the palette changes. Changing to a wholly different GMMP design/view mode must also be accommodated by testing native row layout rather than assuming all themes share the same XML structure.
- Keep GoneSmart's **companion-app** brand palette independent of the **GMMP-injected** UI palette. Where deliberately specified, a lilac/purple GoneSmart sparkle may be overlaid as branding, but do not tint native buttons indiscriminately or change GMMP's white native plus icon without a specific feature reason.
- Multi-playlist selection should mirror GMMP's **Queue multi-selection**: long-press enters selection, selected rows stay highlighted in GMMP's *current* accent color while scrolling, the contextual top bar has a back control and native localized selected count, **no right-hand checkmarks**, and the native confirm FAB stays actionable. The lilac sparkle/confirmation mark was specifically requested; keep its established visual scale.
- Folder icons in the new Playlist folders UI should be **thin/filigree outline folders**, not oversized heavy filled folders. The font must use the **exact native GMMP title rendering from the currently bound row**, not an independently chosen size; do not add extra divider lines or arbitrary gray backgrounds. A 2026-09-25 diagnostic observed a 30 px base `metadataTextEntry` on a 144 px row while the rendered headline looked larger, proving that `TextView.textSize` alone is insufficient: copy native styled text/TextAppearance spans and other runtime typography instead of converting 30 to a fixed 45 px.
- UI lifecycle is as important as styling: never let injected views cover the navigation drawer, mini-player, Now Playing, Queue, other tabs or native FAB. Respect native fragment and picker teardown, cancel deferred render callbacks and avoid structural ViewGroup removal during a fragment's active detach traversal. If a dynamic overlay cannot be made safe for the active GMMP view mode, leave the unmodified native list rather than blocking navigation.
- Validate relevant surfaces in **both** the normal Playlists tab and the **Add to Playlist** picker. Test at least the current theme plus one palette change and, before finalizing broad compatibility, a structurally different GMMP view mode/skin.

## 6. Playlist folders — exact navigation and creation policy

This is an **opt-in feature** in the GoneSmart UI tab, initially **OFF**; Group external playlists and Group root playlists default **ON**. Both options are independent. The same folder navigation/grouping must work in the normal Playlists tab and Add to Playlist picker.

- Read the **complete native GMMP playlist model source**, not a partial sample of currently visible RecyclerView rows. Identity is the native playlist path (observed xn3.q); display and sort by GMMP's native playlist name (observed xn3.p or a verified native name accessor), **not the file basename**. A prior bounded device probe found all **248/248 adapter rows/models** in that particular library (61 internal and 187 external); this is a dated test result, not a hardcoded expected count.
- Do not scan internal storage/SD-card M3Us merely because GMMP's full native playlist model is harder to inspect. Native GMMP already knows the library; the user specifically rejected redundant filesystem scanning as a replacement for finding the complete source. Empty directories, if supported later, need their own explicitly justified source.
- Display, in this order: actual physical folders nested to any depth; optional **virtual Other Locations**; then any ungrouped playlists. Group external playlists determines whether playlists outside the main GMMP root go into virtual Other Locations; Group root playlists independently determines whether playlists directly in GMMP's main playlist directory go there. A real physical directory actually named Other Locations is **distinct** from the virtual node. When root grouping is ON, show the virtual node even if empty so the first main-root playlist can be created there. See the four-option matrix and examples in docs/PLAYLIST_FOLDERS.md.
- **Do not introduce a second folder chooser for creating a playlist.** The currently viewed physical folder is its destination. Apply this exact intended rule in both surfaces:

| Open location | Group root ON | Group root OFF |
| --- | --- | --- |
| Main/root view | Hide creation | Create in GMMP main root |
| Virtual Other Locations | Create in GMMP main root | Hide creation |
| Any real physical subfolder | Create inside that subfolder | Create inside that subfolder |

- In the ordinary Playlists screen, hide **only** the verified native overflow **Hinzufügen / menuAdd** item where creation is forbidden; **NEVER hide the entire three-dot menu**. In the picker, manage only the creation plus FAB. **Multi-select's confirm FAB always remains available whenever destinations are selected, irrespective of the creation rule.** Keep the rest of GMMP's native actions functional.
- **Implementation warning (dated 2026-09-25):** Creating a new M3U directly inside a physical subfolder is an **agreed goal, not yet a verified working native operation**. Until the exact native GMMP configured-root and destination-write callback are identified and verified, visibly guard unsupported physical-subfolder creation rather than silently creating the file in the wrong root. Do not describe the current experiment as a finished release feature.
- Selection may span different folders; it must remain stable by playlist path, work with scrolling and Back, and submit native GMMP writes once for each selected destination. A normal single tap continues to use the real native GMMP action.
- **Do NOT implement Move Playlist yet.** Manually moving M3Us caused stale native database rows and can rewrite relative references. First identify and verify a native GMMP move/rename/reindex path, write permissions and safe rollback; only then implement synchronized file + DB changes. Smart Playlists are distinct native objects; do not handle them as ordinary M3Us without separate proof.
- If native data or UI hooks are incomplete, fail closed to the original playlist list. Never destroy/replace GMMP's playlist DB or move the user's actual files to implement a visual folder grouping.

Read docs/PLAYLIST_FOLDERS.md for all four grouping cases, native class evidence, dated logs, creation requirements and current crash/overlay investigations.

## 7. Multi-playlist selection, Flip, Track Auto-DJ and indicators

- **Multi-playlist add:** user long-presses a destination and can select/deselect multiple paths; GMMP's own native writer handles every addition. Never write/edit M3U files directly for this. Normal one-playlist add, native picker plus/create, context selection and Back must remain intact. Aggregate only verified native completion results; do not navigate backward twice or leave sticky selections. docs/DEVELOPMENT_MULTI_PLAYLIST.md.
- **Queue/playlist Flip:** preserve the unique current native queue entry, playback position and play/pause state while reversing **all** queue entries including history. Distinguish duplicate track IDs by queue-entry ID. New playlist/Smart Playlist Play Flipped reverses GMMP's *resolved complete track list* before playback, never modifies the original M3U or Smart Playlist definition. Use localized native labels and established menu insertion positions. docs/QUEUE_FLIP_TESTING.md.
- **Track Auto-DJ:** a separate optional per-track action after Play next. When triggered, start from the selected native queue entry in a fresh queue and then allow GMMP to fill to its own configured Initial Size. If already running, don't leave racing previous-session refills attached. The corrected native isolation approach was accepted as passed in earlier device testing; **do not require this identical test again without a relevant change/regression**. Use native localized GMMP menu terms and show only one verified visible confirmation. docs/TRACK_MIX_TESTING.md.
- **Player indicator:** add GoneSmart's small sparkle to the existing GMMP Auto-DJ headphones indicator **only on the full Now Playing screen**, not the mini-player/other tabs. Green = smart selection ready, red = error/unavailable/native fallback, absent = disabled/inactive. Do not replace GMMP's whole playback mode UI. The exact icon placement and state must be checked against the active GMMP design. docs/ARCHITECTURE.md and docs/FAQ.md.
- Keep native queue settings and Smart DJ's existing rating/fallback/version matching behavior independent of unrelated UI changes. Do not regress the existing confirmed Flip, Track Auto-DJ and multi-select paths while developing folders.

## 8. Logging, safety, tests and evidence

- Companion **Logs** are concise **English** user-facing high-level events, not a raw Logcat dump. Keep UI-only events from overwriting Smart DJ readiness. One terminal result per action, after verification; no repeated "success" on speculative invocation. See docs/LOGGING.md for category contracts and 400-line retention.
- Use bounded, tagged Logcat diagnostics for obfuscated native probes and real crashes; do not flood production logs, copy private library paths into public issues or accidentally include tokens/signing material. Never commit API secrets, keystores, passwords, private playlists or copyrighted audio.
- Last.fm uses a build-time **LASTFM_API_KEY**. Local builds use ignored local.properties; Actions uses a repository secret. A key inside a shipped client can still be extracted; GitHub Secrets protect source history rather than client binary secrecy. Keep the permanent release signing key and its associated credentials outside the repo. docs/BUILDING.md.
- Unit tests should cover pure logic, folder-group matrix and creation policy, title matching, selection state, queue order/identity and any reported regression. CI success does **not** prove correct GMMP injected UI, fragment lifecycle, live theme, LSPosed hooks or real playlist writes; relevant on-device testing remains mandatory.
- When using observed on-device facts, state exact version, build/commit and the tested screen. Distinguish **confirmed**, **implemented but unverified**, **debug-only**, **planned**, and **blocked pending native GMMP discovery**. Do not present an expected behavior from tests, code or an old assistant reply as a user-verified result.
