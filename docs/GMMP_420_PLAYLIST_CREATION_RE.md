2. Identify the real configured playlist root and exact destination parameter in the create path. Distinguish file writing (`hp3.d`), DB registration/refresh (possible `x6.b`) and success UI. Do not inject an unverified guessed method or write GMMP DB rows directly.

## 2026-09-25 follow-up: both native create lambdas located

A second offline DEX cross-reference pass on the same privately supplied APK identified **two concrete playlist-creation lambdas**, rather than only the event subscriber. The observed instruction references in `classes3.dex` are:

| Native method | Verified bytecode observations | Implication |
| --- | --- | --- |
| `sp3.invoke(Object,Object)` (constructor `sp3(tp3)`) | Resolves a delegated value through `k15.getValue()` / `hr3.getValue()`; concatenates the entered name with `.m3u`; constructs `File(String,String)`; calls `hp3.d()`; obtains the absolute output path; calls `t6.f(Context,String[])`. | **Main Playlists presenter** create-file lambda. Its construction of the destination file is now localized; determine which delegated property supplies its parent directory before introducing a destination hook. |
| `fo3.invoke(Object,Object)` (constructor `fo3(go3)`) | Has the same delegated-value, `.m3u`, `File(String,String)`, `hp3.d()`, absolute-path and `t6.f(Context,String[])` sequence; additionally copies the incoming selected tracks to the new playlist and publishes a result event. | **Add-to-Playlist presenter** create-file lambda. The two surfaces have **separate callbacks but the same file-construction pattern**; modify/verify both, not only the main tab. |
| `rp3.call(Object)` (constructor `rp3(tp3)`) | Builds `File(String)` from a delegated value and calls `x6.b(Context,File)`. | A separate file-registration path associated with the main presenter; its trigger and whether new creation depends on it still need runtime verification. |

### 2026-09-25 correction: native probe method arity

### 2026-09-25: create-only native picker mode (implementation, device test pending)

A deeper offline read of the privately supplied GMMP 4.2.0 APK's actual `fo3.invoke(Object,Object)` bytecode established that its owner `fo3.o` is `go3`, and the Boolean `go3.z` field (initialized from the picker argument `playlistAppend`) **controls whether incoming `ho3.a` tracks are copied into `hp3.r` before the original `hp3.d()` save and `t6.f()` native rescan**. Setting `go3.z=true` only inside `fo3.invoke` makes the original native callback create the playlist without copying the picker source selection. The original Boolean is restored in `finally` so subsequent real playlist additions retain the picker's initial mode. The callback separately emits `j83` via `f2.b(Object)` even in this create-only branch; the existing native close-event interceptor now suppresses just this `j83` when executing in a per-thread create-only scope (not global and not during ordinary selection confirmations). The mode is enabled only with Multi-playlist selection ON, a current attached picker with no selected destinations, and a verified installed `f2.b` guard; unsupported native fields fall back to original GMMP behavior. Both native file save and registration are left untouched. The standard native flow is preserved when Multi-playlist selection is OFF.

The observed 16:27 device log previously showed `MULTI PICKER | view detached` before `fo3.invoke` returned because the original `j83` was emitted. A new device log should instead show `PICKER CREATE ONLY | native close event suppressed` and no picker detach until the user deliberately finishes selection. Check that the new playlist appears from GMMP's native adapter and initially has **zero added tracks**, and that normal multi-add still works after creation. Physical-subfolder creation remains separately guarded until its destination is verified. The CI pipeline must now finish with all Build job steps green before sending the branch for a device test.

### 2026-09-25 device log correction: go3.z is NOT a create-only switch

The 23:10:45 device log confirms the previous hook was entered, logged `native create without tracks`, suppressed the `j83` close event and returned, **yet the maintainer observed the source track in the created playlist**. A fresh direct DEX inspection explains why: `fo3.invoke` reads the source list from `go3.A:ho3.a`; `go3.z` only governs a `hp3.r.clear()` branch, **both Boolean branches then execute `hp3.r.addAll(ho3.a)`**. The previous code and explanatory comments claiming otherwise were wrong. The revised create-only implementation temporarily replaces that **actual source list** with an empty list only during the original synchronous `fo3.invoke`, restores it in `finally`, and separately keeps the existing scoped close-event suppression. If reflective access fails it falls back to native behavior; no direct file/database writes. Device verification is required to confirm the new playlist contains zero tracks and that the original source selection remains available for subsequent multi-add.

### 2026-09-25: confirmed native save-location delegate and scoped physical-subfolder redirect

An additional *direct DEX parse* of the private GMMP 4.2.0 APK identified `vp3.F:k15` as the lazy state for the actual native `playlist_saveLocation` setting. `qv.invoke` (case 4, constructed from `vp3`) obtains this preference via `ya4.d(String,String)`, returning `va4` (an `ua4/hr3` value delegate). Both original create lambdas `sp3.invoke` and `fo3.invoke` call `vp3.F.getValue().getValue()` **immediately before constructing `File(parent, name + ".m3u")`**, then call the original `hp3.d()` writer and `t6.f(Context,String[])` rescan. The scoped `va4.getValue()` hook can return the current physical subfolder only for this precise delegate on the synchronous create thread, without changing the persisted setting or moving an existing M3U.

**Implementation safety gates:** the normal menu is enabled only if the scoped native getter and the `sp3` hook both install; the picker FAB requires the getter and `fo3`. Each physical-create callback rechecks its live folder against the indexed native GMMP root, ensures the directory still exists and that `vp3.F`'s actual configured preference canonicalizes to that exact root. It dry-runs the intercepted getter with no file writes and confirms the requested destination is returned before calling the original native writer inside the same thread-local substitution. A failed gate cancels with a debug error instead of writing in the wrong root. Root and virtual Other Locations keep untouched native writes, and existing multi-add confirmation remains ahead of picker creation. The native `hp3.d()` / `t6.f()` transaction remains intact. **Still requires device verification** for nested main/picker physical folder creation, indexing, and filesystem permissions; CI cannot establish real GMMP behavior.
