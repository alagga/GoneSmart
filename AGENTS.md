## 2. Identity, scope and architecture

- Repository: **alagga/GoneSmart**. Android application ID/package: **io.github.alagga.gonesmart**. Visible app name: **GoneSmart**. LSPosed/Vector target scope: **gonemad.gmmp**. The local Android Studio project has been kept at C:\Android\Projects\GoneSmart.
- The tested target for the current obfuscated hooks is **GoneMAD Music Player (GMMP) 4.2.0**. libxposed API **102**. Android/Kotlin, Gradle Kotlin DSL, companion app plus module. Never claim a different GMMP or framework version works without testing it.
- GoneSmart extends GMMP rather than replacing its playback engine. GMMP owns playback, its queue lifecycle, Auto-DJ request timing, existing queue-size settings and normal controls. Smart Auto-DJ replaces **track selection only** when enabled; native GMMP Auto-DJ remains the configurable fallback. GoneSmart is controlled from its **own companion app**, not by inventing a fifth GMMP Auto-DJ mode.
- The main external recommendation inputs are **ListenBrainz and Last.fm**, matched only to tracks actually in GMMP's local database. No provider suggestions are streamed. Limit network searches and retries as documented in docs/ARCHITECTURE.md and docs/PROVIDERS.md; do not casually change the established selection/fallback algorithm when working on UI.
- Optional UI features (multi-playlist selection, playlist folders, Flip, Track Auto-DJ) are independent of Smart DJ unless their documented action explicitly enables it. Prefer isolated, version-guarded hooks. Passive hooks must preserve the original GMMP result/side effects (call the original chain); intercept or alter behavior only for the specifically enabled feature and verified target.
- Obfuscated GMMP classes and fields are **version-specific observations**, never a stable upstream API. Verify model bindings and callbacks from actual code/device logs, fail closed to native GMMP behavior if a hook or complete model is unavailable, and do not guess dangerous write methods.

### Mandatory native-first investigation gate (maintainer decision 2026-09-26)

**For EVERY feature or behavior inside GMMP, first investigate whether GMMP already implements it anywhere, even on a different screen, menu, dialog, animation, layout or feature. Reuse GMMP's ORIGINAL existing methods, event/callback flow, UI resources, widget/layout classes, RecyclerView mechanics, selection state, native animations and data transactions wherever they exist.** This is a firm default for all future work, not just playlist folders. Only create a GoneSmart-specific implementation when (a) investigation confirms no corresponding native implementation exists, or (b) the maintainer explicitly requests a custom presentation/behavior. Never substitute an approximate lookalike, hardcoded spacing, manually copied timings, extra file manager or synthetic data write merely because native discovery takes effort.

**Required workflow before implementation:** (1) inspect the installed/tested GMMP APK, actual obfuscated call sites, resource XML, bind-time properties and/or live device logs for the requested behavior; (2) write down the original native source method/class/layout, its lifecycle and verified safe reuse boundary; (3) plan to call/inflate/reuse that exact native implementation, including its already-available settings/theme/localization/animations; (4) if native state cannot safely be shared (e.g. a live RecyclerView adapter or animator), instantiate an **independent instance of the verified same native implementation** when technically possible, retaining its real resource layout and behavior, never mutating/sharing the original live object's queues; (5) if any factual, visual or reuse question remains unresolved, **ASK THE MAINTAINER BEFORE implementing a substitute** rather than guessing. A narrowly scoped read-only diagnostic to discover the true native mechanism is allowed; label it as diagnostic, not a finished feature. Record verified evidence and specific version limits in docs/ and tests. Investigate both classloaders before interpreting a Kotlin cast failure as absence of a host AndroidX component. Do not conflate green CI with verified native runtime parity.

See docs/ARCHITECTURE.md, docs/PROVIDERS.md, docs/BUILDING.md and the feature-specific docs below.

Inspect full job logs and fix all failures before sharing a commit as ready for device testing.** `fetch_commit_workflow_runs` currently filters PR runs and is NOT sufficient for push CI: query the repository Actions runs for the branch and verify the matching `head_sha`, then inspect that run's jobs and steps. Never describe a running or missing CI run as successful. Keep polling or explicitly disclose if CI is unavailable; do not ask the maintainer to debug an already failing GitHub build. Successful multi-add reports file count and successful destination count **once**; Track Auto-DJ likewise displays one verified success confirmation. Genuine errors remain visible.
5. Preserve official GMMP wording where possible rather than silently renaming native functions; use **Track Auto-DJ** consistently in the English companion. ## 5. GMMP design and theme integration — standing rule

- The optional injected UI should look and behave **as though GMMP built it**. Match the **actual active GMMP view mode/skin**, row height, headline font family and size, padding, icon alignment, selectable ripple, background, menu/FAB style and selection behavior. No invented separator lines where the original has none. Do not mistake a small metadata TextView for the primary playlist headline. Show the true native playlist display name, not the M3U filename.
- **Never hardcode or approximate GMMP runtime design values when the native view already exposes them.** This includes colors, font size, font scaling, Typeface, TextAppearance/spans, row height, padding, margins, gravity, ripple/background, selection state, FAB style and layout/view-mode structure. Clone/read the **actual currently-bound native view** and its styled text at runtime, including Android font-scale/device-density effects. Static px/sp multipliers, guessed ratios such as “30 px → 45 px”, screenshot-derived constants and one-device tuning are acceptable only as explicitly documented **defensive fallbacks when no native source exists**, never as the primary implementation. Follow the live GMMP Aesthetic/theme sources (current primary, accent, native FAB color, surface/background and text state). The user may set a manual color or enable a dynamic palette derived from the playing cover; update visible UI, selection highlights and branded decoration when the palette changes. Changing to a wholly different GMMP design/view mode must also be accommodated by testing native row layout rather than assuming all themes share the same XML structure.
- Keep GoneSmart's **companion-app** brand palette independent of the **GMMP-injected** UI palette. Where deliberately specified, a lilac/purple GoneSmart sparkle may be overlaid as branding, but do not tint native buttons indiscriminately or change GMMP's white native plus icon without a specific feature reason.
- Multi-playlist selection should mirror GMMP's **Queue multi-selection**: long-press enters selection, selected rows stay highlighted in GMMP's *current* accent color while scrolling, the contextual top bar has a back control and native localized selected count, **no right-hand checkmarks**, and the native confirm FAB stays actionable. The lilac sparkle/confirmation mark was specifically requested; keep its established visual scale.
- Folder icons in the new Playlist folders UI should be **thin/filigree outline folders**, not oversized heavy filled folders. The font must use the **exact native GMMP title rendering from the currently bound row**, not an independently chosen size; do not add extra divider lines or arbitrary gray backgrounds. A 2026-09-25 diagnostic observed a 30 px base `metadataTextEntry` on a 144 px row while the rendered headline looked larger, proving that `TextView.textSize` alone is insufficient: copy native styled text/TextAppearance spans and other runtime typography instead of converting 30 to a fixed 45 px.
- **Native component reuse (clarification 2026-09-26):** do not substitute an approximate Android `View.animate` or `HorizontalScrollView` for GMMP's actual mechanics when the actual native class is available. In the overlay, use the SAME runtime AndroidX RecyclerView (1.4.0 in supplied GMMP 4.2.0), native Files quickNav's live EdgeEffectFactory/scroll configuration, and for a verified pure insertion instantiate GMMP's live `ItemAnimator` concrete class separately with the native durations and interpolation implemented by that class. Do not reparent GMMP's actual RecyclerView or share its live ItemAnimator, since that would corrupt native UI state. Use an explicit logged fallback if a future custom class cannot be instantiated; never claim pixel-exact behavior without device verification. Preserve original GMMP row XML/menu/selection and the root/picker create semantics.
- **Native Playlists row context:** every individual playlist in the normal Playlists tab keeps GMMP's current-view-mode three-dot `rvContextMenu` control and all of its original localized context actions. Reuse the actual native row's button/icon/tint and dispatch only against a holder whose bound native `xn3.q` matches the requested playlist path, including offscreen rows. Do **not** put this control on folder navigation rows, fabricate a parallel GoneSmart action list or substitute the top-toolbar overflow menu for a playlist's own menu.
- **Playlist breadcrumb parity:** nested folders show a fixed horizontal breadcrumb above the scrolling list, matching GMMP's native Files/Folder tab `quickNavRecyclerView` typography, dynamic color, overscroll/stretch and native rounded touch feedback where observed. **On first Add-picker opening**, before GMMP's own Files quickNav is instantiated, use the empirically measured native-to-native title ratio as a per-version fallback; persist and prefer real runtime sampled typography when available. Preserve manual horizontal scroll across theme/layout/playlist-selection refreshes; keep the same breadcrumb child views when its content and live style are unchanged; scroll to the newest path component only after actual folder navigation. Let current and ancestor segments all show the native pressed-state animation, deferring actual ancestor navigation by one animation frame. **Folder rows have NO extra trailing › arrow after the folder name** (breadcrumb separators remain). The root shows **no breadcrumb and takes no extra height**. Inside a folder, begin with GMMP's **localized `storage`** string (e.g. Speicher); every earlier segment navigates directly to that ancestor. Remove the old synthetic single-tap Back row; normal Android Back still goes up one folder. The breadcrumb is also displayed in the Add picker.
- UI lifecycle is as important as styling: never let injected views cover the navigation drawer, mini-player, Now Playing, Queue, other tabs or native FAB. Respect native fragment and picker teardown, cancel deferred render callbacks and avoid structural ViewGroup removal during a fragment's active detach traversal. If a dynamic overlay cannot be made safe for the active GMMP view mode, leave the unmodified native list rather than blocking navigation.
- Validate relevant surfaces in **both** the normal Playlists tab and the **Add to Playlist** picker. Test at least the current theme plus one palette change and, before finalizing broad compatibility, a structurally different GMMP view mode/skin.
